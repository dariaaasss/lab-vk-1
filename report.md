# Практическая работа 1

## 1. Вариант

| Поле | Значение |
|---|---|
| ФИО | Булаева Дарья |
| Вариант | 2, TPC-H Q10 |
| Масштаб | `sf2` |

Выбрала `sf2`, чтобы работать с несколькими миллионами строк и при этом выполнить все замеры локально. В этом масштабе получается 300 тысяч клиентов, 3 миллиона заказов и почти 12 миллионов позиций. Данные создаёт коннектор Trino `tpch`.

## 2. Стек

| Сервис | Для чего используется | Причина выбора |
|---|---|---|
| Silo `RELEASE.2026-09-03T13-18-01Z` | Хранит файлы таблиц через S3 API | Можно работать с объектным хранилищем на своём компьютере. Подходит для подключения Trino и Spark. |
| PostgreSQL 17.11 | База каталога | Lakekeeper сохраняет в ней сведения о зарегистрированных таблицах. |
| Lakekeeper 0.14.0 | Каталог Iceberg | Оба движка получают из одного каталога схему таблицы и её текущую версию. |
| Trino 476 | Загрузка TPC-H и выполнение SQL | Поддерживает нужные форматы файлов и смену кодека при записи. |
| Spark 3.5.5 | Дополнительная проверка Bronze | Работает с теми же таблицами Iceberg, поэтому данные не приходится повторно выгружать для другого инструмента. |

MinIO скачать не получилось, поэтому для хранения файлов выбрала Silo с поддержкой S3 API.

Настройки сервисов находятся в `compose.yaml`. Для запуска использовались следующие команды:

```powershell
docker compose up -d --wait --wait-timeout 180
python jobs/run.py setup
python jobs/run.py bench
python jobs/run.py build
python jobs/dependencies.py
docker compose --profile tools run --rm spark
python jobs/run.py inspect
```

`setup` создаёт бакет и каталог, `bench` записывает Bronze и проводит замеры, `build` собирает Silver и Gold. Последний этап сохраняет размеры таблиц. Весь запуск собран в `run.ps1`.

## 3. Что считает Q10

Нужно найти 20 клиентов с наибольшей суммой возвращённых позиций. Берутся заказы с 1 октября по 31 декабря 1993 года и строки с `returnflag = 'R'`. Сумма позиции считается как `extendedprice * (1 - discount)`.

| Таблица | Используемые колонки | Операции |
|---|---|---|
| `customer` | `custkey, name, acctbal, nationkey, address, phone, comment` | Соединение с заказами и страной, данные клиента для результата. |
| `orders` | `orderkey, custkey, orderdate` | Отбор квартала и связь клиента с позициями. |
| `lineitem` | `orderkey, extendedprice, discount, returnflag` | Отбор возвратов и расчёт суммы с учётом скидки. |
| `nation` | `nationkey, name` | Название страны. |

Исходный Q10 из `sql/q10.sql` выполнен на `tpch.sf2`. Его результат служит проверкой для остальных таблиц.

## 4. Хранение и обработка

Размеры в таблицах указаны в МБ, один МБ равен 1 000 000 байт. Это сумма активных файлов данных из Iceberg `$files`. Метаданные и предыдущие версии в этот размер не входят.

### Bronze

В Bronze скопированы нужные колонки исходных таблиц без фильтрации строк. Основная схема `lake.bronze` записана в Parquet с ZSTD. Остальные схемы содержат те же данные для сравнения кодеков.

| Таблица | Колонки | Строк | Размер, МБ | Формат | Кодек | Партиции | Обоснование |
|---|---|---:|---:|---|---|---|---|
| `customer` | `custkey, name, acctbal, nationkey, address, phone, comment` | 300 000 | 16,284248 | Parquet | ZSTD | Нет | Справочник занимает около 16 МБ. Отдельные партиции по странам для Q10 не нужны. |
| `orders` | `orderkey, custkey, orderdate` | 3 000 000 | 16,269608 | Parquet | ZSTD | Нет | После выбора трёх колонок размер небольшой. Оставлен один файл, чтобы не дробить его по датам. |
| `lineitem` | `orderkey, extendedprice, discount, returnflag` | 11 997 996 | 63,059523 | Parquet | ZSTD | Нет | Основной объём данных, но и он помещается в один файл. Для бенчмарка структура хранения одинакова во всех вариантах. |
| `nation` | `nationkey, name` | 25 | 0,000632 | Parquet | ZSTD | Нет | Всего 25 строк. |

Bronze занимает 95,614 МБ. Выбор Parquet + ZSTD основан на сравнении в разделе 5.

### Silver

Перед обработкой проверены число строк, ключи, связи между таблицами, цены и скидки. Ошибок не найдено.

В `customer_directory` к клиенту добавлено название страны. В `order_returns` сначала отобраны возвраты нужного квартала, затем позиции сгруппированы по заказу. Получилось 98 352 строки вместо 229 871 позиции, то есть примерно на 57% меньше. Сумма `returned_positions` сверена с числом исходных отобранных позиций, а `orderkey` в этой таблице уникален.

| Таблица | Колонки | Строк | Размер, МБ | Формат | Кодек | Партиции | Обоснование |
|---|---|---:|---:|---|---|---|---|
| `customer_directory` | `custkey, name, acctbal, nation, address, phone, comment` | 300 000 | 16,297377 | Parquet | ZSTD | Нет | Название страны уже подставлено, в Gold достаточно соединить клиента с суммами заказов. |
| `order_returns` | `orderkey, custkey, orderdate, returned_positions, returned_value, analyst_note` | 98 352 | 1,180508 | Parquet | ZSTD | Нет | Одна строка на заказ. При построении Gold обрабатывается меньше строк, а файл занимает около 1 МБ. |

Колонка `analyst_note` добавлена в опыте с изменением схемы.

### Gold

В Gold суммы заказов объединяются по клиенту. После сортировки остаются первые 20 строк.

| Таблица | Колонки | Строк | Размер, МБ | Формат | Кодек | Партиции | Обоснование |
|---|---|---:|---:|---|---|---|---|
| `customer_refunds` | `custkey, name, revenue, acctbal, nation, address, phone, comment` | 20 | 0,003261 | Parquet | ZSTD | Нет | Итог для просмотра. При таком размере можно оставить формат Silver. |

На первом месте клиент `104737`, сумма возвратов `816993,2685`. Все строки сохранены в [top20.csv](results/top20.csv).

Состав топ-20, реквизиты и названия совпали с исходным Q10. Для сумм использован допуск `rel_tol=1e-9`, `abs_tol=1e-6`, поскольку цены имеют тип `DOUBLE`. Максимальное расхождение после группировки по заказам составило `2,33e-10`.

## 5. Сравнение форматов

### Как проводились замеры

Стенд работает на Windows через Docker Desktop и WSL2. Процессор i5-12450H, оперативная память 16 ГиБ. Для Docker выделено около 7,6 ГиБ, Trino ограничен четырьмя CPU и 3 ГиБ памяти, Java heap составляет 2 ГиБ. S3-файлы находятся в папке на диске D, подключённой в контейнер.

Для каждого сочетания формата и кодека выполнены три записи четырёх таблиц. Время записи включает генерацию TPC-H, сжатие и сохранение данных. Затем для каждого варианта сделан один прогревочный запрос и пять измерений Q10. Порядок вариантов между повторами менялся. Spark запускался после этих замеров.

Использовались одинаковые настройки `task_concurrency=4`, `task_min_writer_count=1` и `task_max_writer_count=1`. В текущей версии каждой таблицы получился один файл. В таблице ниже указаны медианы времени и размеры после третьей записи. Время взято из `elapsedTimeMillis` Trino, включая планирование запроса. Для записи сложено время четырёх CTAS.

### Результаты

| Формат | Кодек | Bronze, МБ | Запись, с | Q10, с | Вывод |
|---|---|---:|---:|---:|---|
| Parquet | ZSTD | 95,614 | 14,686 | 2,004 | Самый маленький общий размер и наименьшая медиана записи. |
| Parquet | GZIP | 96,206 | 27,109 | 2,396 | Почти тот же размер, но запись заметно дольше. |
| ORC | ZSTD | 104,514 | 14,875 | 1,806 | Наименьшая медиана Q10, при этом больше всего места на диске. |
| ORC | GZIP (ZLIB) | 101,190 | 19,986 | 2,187 | По этим замерам уступает Parquet + ZSTD и по размеру, и по времени. |

Для основного слоя выбрала Parquet + ZSTD. Он записался примерно на 46% быстрее Parquet + GZIP. ORC + ZSTD прочитал Q10 примерно на 10% быстрее Parquet + ZSTD, но его файлы больше примерно на 9%. Для этой работы меньший размер оказался предпочтительнее разницы около 0,2 секунды на запросе.

Результаты относятся к Q10 и выбранным колонкам. Например, отдельная `lineitem` с Parquet + GZIP занимает немного меньше места, чем с ZSTD. Все замеры сохранены в CSV в папке `results`. Ответ каждого Q10 сравнивался с исходным запросом.

В файлах ORC настройке GZIP соответствует ZLIB. Это проверено по файлам `nation`.

### Метаданные и прогрев

Для Parquet + ZSTD активные данные занимают 95,614 МБ, метаданные с историей 1,175 МБ. Общий размер объектов этих таблиц составляет 287,968 МБ: после трёх записей `CREATE OR REPLACE TABLE` сохранил и прошлые версии. У `nation` файл данных занимает 632 байта, а накопленные метаданные 44 091 байт. Поэтому размер маленькой таблицы нельзя оценивать только по её данным. Время запросов при разном количестве снапшотов отдельно не сравнивалось.

Первый Q10 на Parquet + ZSTD выполнился за 4,011 с, медиана следующих запусков составила 2,004 с. Кэши не очищались. Сравнение форматов сделано после прогрева, а влияние кэша и JVM по отдельности не измерялось.

## 6. Работа с Iceberg и Spark

### 6.1. Схема и версии таблиц

| Вопрос | Ответ |
|---|---|
| Для чего нужен lakehouse? | Когда история занимает много места и её читают разные инструменты, удобно хранить общие файлы отдельно от вычислений. Iceberg ведёт схему и версии этих файлов. Здесь один набор данных доступен из Trino и Spark. Для небольшой задачи с одним приложением обычная БД потребовала бы меньше сервисов. |
| Как изменилась схема Silver? | В `order_returns` добавлена строковая колонка `review_note`, затем переименована в `analyst_note`. Во всех 98 352 строках она равна `NULL`. Пути и размеры файлов до и после изменения совпали. |
| Как восстановлены данные? | В Gold для клиента 104737 сумма заменена на 0. Чтение прежнего снапшота вернуло 816993,2685. После отката эта сумма снова появилась в текущей таблице, и весь топ-20 совпал с исходным запросом. |

Изменение схемы:

```sql
ALTER TABLE lake.silver.order_returns ADD COLUMN review_note VARCHAR;
ALTER TABLE lake.silver.order_returns RENAME COLUMN review_note TO analyst_note;
```

Проверка восстановления:

```sql
UPDATE lake.gold.customer_refunds SET revenue = 0 WHERE custkey = 104737;

SELECT revenue FROM lake.gold.customer_refunds
FOR VERSION AS OF 4671655699032731848 WHERE custkey = 104737;

ALTER TABLE lake.gold.customer_refunds
EXECUTE rollback_to_snapshot(4671655699032731848);
```

Номер снапшота берётся перед обновлением, при повторном запуске скрипт подставит другой номер. Откат возможен, пока сохранены нужный снапшот и его данные.

### 6.2. Чтение Bronze в Spark

Для дополнительного инструмента выбрала Spark. Он читает Iceberg через REST-каталог и позволяет выполнить тот же SQL по Bronze. Контейнер запускается командой:

```powershell
docker compose --profile tools run --rm spark
```

Настройки подключения находятся в `jobs/spark_check.py`: каталог `http://lakekeeper:8181/catalog`, warehouse `returns`, S3 endpoint `http://minio:9000`. В Spark таблицы называются `lake.bronze.*`.

Скрипт вывел первые пять клиентов, посчитал строки всех четырёх таблиц и выполнил Q10 из файла SQL. Количество строк совпало с Trino, итоговые 20 клиентов тоже совпали. В консоли получено:

```text
SPARK_BRONZE_OK {"customer": 300000, "orders": 3000000, "lineitem": 11997996, "nation": 25} Q10: 11.630 s, 20 rows
```

Полный вывод находится в [spark_console.txt](results/spark_console.txt). Spark запускался один раз на двух CPU для проверки подключения. Сравнение скорости двух движков по этому запуску не проводилось.

## 7. Итог

Группировка возвратов по заказам сократила Silver с 229 871 позиции до 98 352 строк и сохранила результат Q10. Parquet + ZSTD выбран из-за небольшого размера и быстрой записи, хотя ORC + ZSTD показал лучшее время чтения запроса. Старые версии заметно увеличивают общий объём файлов, а у маленьких таблиц метаданные могут быть больше данных. При изменении схемы файлы Silver остались прежними, а ошибочное обновление Gold удалось отменить через снапшот. Проверка в Spark подтвердила, что к таблицам можно обращаться из другого движка через тот же каталог.
